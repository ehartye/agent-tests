# Doctrine

The rules the agent-tests skills teach, each with the evidence behind it. `tests/doctrine.test.ts` pins the rule titles and the shape of each section.

How to read a rule:
- `Claim:` is what the skills may assert.
- `Evidence:` cites a page in the wiki-master vault (`wiki/...`, relative to the vault root) or a URL. Every cited page was read when this file was written (2026-10-11).
- `Opinion:` marks a rule, or part of one, that no source settles. It says what evidence would change the view.
- `Note:` lines record limits, counter-evidence and how the claim differs from the seed claim in the plan.

## Rule: Efficiency is protection per unit of cost
Claim: A test is worth keeping when the risk it protects against outweighs what it costs to run, read and maintain; neither the number of tests, nor coverage, nor speed alone says whether a suite is healthy.
Evidence: wiki/sources/google-swe-book-testing-overview.md — Google says tests derive their value from the trust engineers place in them, that a bad suite can be worse than none, that "do we have enough tests?" cannot be answered with one number, and that teams should refactor slow or marginal tests.
Evidence: wiki/sources/vocke-practical-test-pyramid.md — Vocke says every test is "additional baggage" that costs time to write, read, maintain and run, and advises deleting higher-level tests already covered at a lower level.
Evidence: wiki/sources/dodds-testing-trophy.md — Dodds frames testing as return on investment, where the return is confidence and the investment is time.
Evidence: wiki/sources/istqb-ctfl-syllabus-v4.md — ISTQB says exhaustive testing is impossible and effort should be focused with prioritization and risk-based testing.
Evidence: wiki/authored/no-claudes-sky/notes/test-strategy-review.md — The owner's own Planetforge review judged a 3,028-test suite by meaningful failures, defects caught and runtime, not by its headline count.
Note: Google's "test everything that you don't want to break" (Beyoncé Rule) pulls the other way; the rule does not license deleting tests that protect something, only tests whose protection is duplicated or absent.

## Rule: Run frequency multiplies cost
Claim: A test's cost scales with how often it runs, so moving slow or broad tests out of the edit loop into later lanes (pre-merge, scheduled, release) usually saves more than deleting them, provided each lane still runs often enough to keep the set of suspect changes small.
Evidence: wiki/sources/google-swe-book-continuous-integration.md — Google runs "only fast, reliable" tests on presubmit because running everything there is "too expensive", catches the rest on post-submit, and moving end-to-end tests from after the nightly deploy to a two-hourly post-submit run cut the culprit set by 12 times.
Evidence: wiki/sources/google-swe-book-testing-overview.md — Google teams often run large tests "only during the build and release process so as not to impact developer workflow", and note that a slower suite is run less often and so gives less benefit.
Evidence: wiki/sources/dora-continuous-integration-capability.md — DORA says tests should take no more than a few minutes, with an upper limit of about ten, and recommends splitting longer-running tests into a separate build, and warns that tests run infrequently make a failure hard to trace to one change.
Evidence: wiki/sources/vocke-practical-test-pyramid.md — Vocke puts fast tests in the early pipeline stages and slower, broader tests later, staged by speed and scope rather than by test type.
Note: The seed said frequency lanes save "more than deleting"; the sources support lanes but also show the price of a lane that runs too rarely (a large culprit set), so the claim now carries that condition.

## Rule: Test size and layers
Claim: Classify tests on two separate axes: size (what a test needs to run: one process, one machine, or more), which predicts speed and determinism and so decides how often it runs; and scope (how much code it validates), which decides what it protects and whether it duplicates another test; the pyramid, trophy and honeycomb agree on few broad tests and fast, reliable tests first, and disagree mainly on where the bulk of tests sits and how much to mock, and only Google gives numbers, which it calls a rough guideline; so the audit reports a suite's shape and never scores it against a proportion target.
Evidence: wiki/sources/google-swe-book-testing-overview.md — Google separates size (small runs in one process, medium on one machine, large anywhere) from scope, classifies every test by size, gives a rough 80/15/5 scope mix that "every team's mix will be a little different", and names the ice-cream-cone and hourglass anti-patterns.
Evidence: wiki/sources/google-test-sizes.md — The 2010 Google Testing Blog post defines small, medium and large tests by the resources they may use, with time limits per size.
Evidence: wiki/sources/google-swe-book-continuous-integration.md — Most Google teams run small tests on presubmit, while whether to run larger tests there "varies by team".
Evidence: wiki/sources/vocke-practical-test-pyramid.md — Vocke's pyramid asks for lots of small fast unit tests, some coarser tests and very few high-level tests, and calls the shape "overly simplistic" and its layer names a local convention.
Evidence: wiki/sources/dodds-testing-trophy.md — The trophy (static, unit, integration, end-to-end) puts most effort into integration tests, adds static checks because JavaScript lacks them by default, and was meant for monoliths.
Evidence: wiki/sources/spotify-testing-honeycomb.md — Spotify's honeycomb for microservices favours integration tests, few implementation-detail tests and ideally no integrated tests, because many unit tests lock in internal structure.
Evidence: wiki/sources/coding-agents-over-mocked-tests.md — Coding agents add mocks in 36% of their test commits against 26% for non-agents, so applying a "lots of unit tests" target to agent output would likely reward mock-heavy tests (this doctrine's inference, not the paper's).
Opinion: Inferring a test's size from what it imports and calls (rather than trusting a declared label) and never targeting a proportion are this doctrine's choices for agent-built suites; whether size-plus-scope lanes catch more agent-introduced defects than a pyramid target is unmeasured, and a mutation-testing comparison on the owner's repositories would settle it.
Note: Perspective research (ADR in the vault at wiki/authored/agent-tests/decisions/test-shape-for-agent-built-suites-adr.md) found the seed's "size or layer" framing hid that Google uses both axes for different jobs, and that a "lots of unit tests" target would likely reward agents' mock-heavy tests; the claim was revised accordingly.

## Rule: Flaky tests cost more than their runtime
Claim: A flaky test costs reruns, investigation and, worst, trust: once failures are routinely dismissed, real failures are dismissed too; so a flaky test is fixed, or quarantined out of the gating lanes with an owner and a time or count limit, and a quarantine is not a resting place because it can hide real bugs.
Evidence: wiki/sources/google-flaky-tests-at-google.md — Google reports that about 84% of observed pass-to-fail transitions involve a flaky test, that legitimate failures in flaky tests are commonly ignored, and that automatic quarantine "could easily mask a real race condition".
Evidence: wiki/sources/fowler-eradicating-non-determinism.md — Fowler calls non-deterministic tests useless and "a virulent infection", and advises quarantining them out of the main pipeline but fixing them quickly, with a numeric or time limit on the quarantine.
Evidence: wiki/sources/google-swe-book-continuous-integration.md — Google says flaky tests erode confidence like a broken test and that some teams remove them from presubmit temporarily while they are fixed, tracking disabled tests so the suite does not become a pile of old disabled tests.
Evidence: wiki/sources/dora-continuous-integration-capability.md — DORA asks for reliable tests so that a failure means a real problem.
Note: The seed said flakiness is "not tolerated"; Google reports it lives with a baseline flake rate because the insertion rate matches the fix rate, so the claim now says what to do with a flaky test rather than promising zero.

## Rule: Run only affected tests in the edit loop
Claim: In the edit loop, run only the tests affected by the change (vitest `related` or `--changed`, jest `--findRelatedTests` or `--onlyChanged`), and keep a full run in a later lane, because selection by static imports misses dynamically loaded code and any selection can miss a regression.
Evidence: wiki/sources/vitest-cli-guide.md — `vitest related` runs only tests that cover the listed source files and works with static imports but not dynamic ones; `--changed` runs tests affected by changed files.
Evidence: wiki/sources/jest-cli-options.md — Jest's `--findRelatedTests` runs "the minimal amount of tests necessary" for given files, and `--onlyChanged` needs a static dependency graph with no dynamic requires.
Evidence: wiki/sources/meta-predictive-test-selection.md — Meta's predictive test selection catches more than 99.9% of regressions before they reach trunk while running about a third of the tests that transitively depend on the change, and every change is still tested exhaustively before it goes to production.
Evidence: wiki/sources/google-swe-book-continuous-integration.md — Google restricts presubmit tests to the project being changed, or selects them with a model predicting their chance of catching a failure, and catches what slips through on post-submit.

## Rule: No compatibility tests without consumers
Claim: Compatibility, migration and fallback behaviour exists to protect consumers of an interface; before 1.0 and with no consumers outside the repository, tests of old behaviour protect nothing and lock in an API that SemVer says may change at any time; once anyone depends on the interface, Hyrum's Law says they will depend on more of it than was promised.
Evidence: wiki/sources/semantic-versioning-2-0-0.md — SemVer says major version zero is for initial development, anything may change at any time, and the public API should not be considered stable; it also says software used in production should probably already be 1.0.0.
Evidence: wiki/sources/hyrums-law.md — With enough users of an API, all observable behaviours will be depended on by somebody, which is why compatibility constrains changes; the law is conditional on having users.
Note: Neither source mentions tests directly; applying them to tests is this doctrine's inference. The check before removing such a test is whether any consumer exists: a published package, a plugin installed from the repository, stored data in an old format, or another repository.

## Rule: Automatic CI on every push for a solo pre-release project
Claim: For one developer who merges feature branches through pull requests, blocking CI, an OS matrix or CI on every branch push mostly repeats the local merge run at the price of waiting, flaky alarms and metered minutes, so the OS matrix belongs on demand, on a schedule and on release; but one non-blocking Linux job per pull-request update is still recommended, because it independently checks what an agent reports and keeps the set of suspect commits to one, and it may be dropped only when the local merge gate is written by a tool over a clean tree and the minutes are metered.
Evidence: wiki/sources/fowler-continuous-integration.md — Counter-evidence to the seed: Fowler says every push to mainline should trigger a build in a reference environment because of lapses in discipline and differences between workspaces, so a failure points at the latest push; he applies the CI service to the mainline only and frames CI for a committed team, not a solo developer.
Evidence: wiki/sources/dora-continuous-integration-capability.md — Counter-evidence to the seed: DORA says each commit should trigger a build and a fast automated test run, and lists not running quick tests on every change as a pitfall; its framing is many developers working on related systems.
Evidence: wiki/sources/istqb-ctfl-syllabus-v4.md — Counter-evidence to the seed: ISTQB treats CI with automated regression tests as good practice and part of shift left.
Evidence: wiki/sources/google-swe-book-continuous-integration.md — Supports keeping the blocking gate small: Google runs "only fast, reliable" tests on presubmit because waiting is costly, and notes CI becomes more necessary as a codebase ages and grows; it also shows that running tests more often shrinks the culprit set (12 times in the Takeout case).
Evidence: wiki/sources/google-flaky-tests-at-google.md — Supports limiting how often a solo owner is alarmed: most pass-to-fail transitions at Google involve a flaky test, and people learn to ignore alarms with a history of false signals.
Evidence: wiki/sources/github-actions-billing.md — Standard GitHub-hosted runners are free for public repositories, while private repositories spend a monthly minutes quota, so a single Linux job costs little and the matrix is where the money goes.
Evidence: wiki/sources/coding-agents-over-mocked-tests.md — Coding agents touch test files in 23% of their commits against 13% for non-agents, so a merge gate that the agent reports on itself is run by the party whose commits more often touch tests.
Opinion: No source studies a solo, pre-release, agent-built project; the split between a non-blocking pull-request job and an on-demand or scheduled matrix is this doctrine's judgment, built from team-oriented sources. Measuring, for a month, how often the local merge stamp and a hosted run disagree, together with merges to main per day and flake rate, would confirm or overturn it; a disagreement rate near zero would support dropping the mainline job.
Note: This contradicts the seed claim, which said on-demand, scheduled and release-tag runs deliver the clean-environment value with no on-push run. Perspective research (ADR in the vault at wiki/authored/agent-tests/decisions/solo-pre-release-ci-triggers-adr.md) agreed the matrix and blocking checks on push are waste, but found that a weekly schedule leaves a week of agent commits to search and that an agent-written local stamp is self-reporting. CI on push also does not catch an agent weakening the tests: it runs whatever suite was pushed.
Note: Amended 2026-10-11 after the owner said they never push to the default branch and work only through feature branches and pull requests: the recommended job runs on `pull_request` (path-filtered, drafts skipped, newer runs cancel older ones), not on push to main, and no post-merge run is recommended because the pull-request job already ran on the same tree.

## Rule: Windows and macOS runners cost more than Linux
Claim: For private repositories, GitHub-hosted Windows and macOS runners bill more per minute than Linux (at 2026-10-11: Linux 2-core $0.006, Windows 2-core $0.010, macOS 3- or 4-core $0.062), so an OS matrix is the main cost driver of a workflow; standard GitHub-hosted runners are free for public repositories.
Evidence: wiki/sources/github-actions-runner-pricing.md — GitHub's runner pricing table, read 2026-10-11, lists $0.006 per minute for Linux 2-core x64, $0.010 for Windows 2-core and $0.062 for macOS 3-core or 4-core, rounded up to whole minutes per job.
Evidence: wiki/sources/github-actions-billing.md — GitHub's billing page says Windows and macOS jobs cost more than Linux jobs, that Actions is free for public repositories on standard runners, and that private repositories get a monthly quota of included minutes (2,000 on GitHub Free).
Note: The seed's "minute multipliers" wording no longer appears in GitHub's billing docs read on 2026-10-11; the difference is expressed as per-minute rates. The claim was narrowed to private repositories because public ones are free.

## Rule: Bare vitest can start watch mode in an interactive terminal
Claim: Bare `vitest` (and `vitest watch` or `vitest dev`) starts watch mode only when stdin is a TTY, the `CI` environment variable is unset and Vitest does not detect an AI coding agent; otherwise it behaves like `vitest run`; `vitest run` and `--run` always exit, so scripts, hooks and agents should use them; jest is the reverse and watches only with `--watch` or `--watchAll`.
Evidence: wiki/sources/vitest-watch-config.md — The `watch` option defaults to `!process.env.CI && process.stdin.isTTY`, and to `false` when Vitest detects an AI coding agent; in CI or a non-interactive shell watch mode is not the default.
Evidence: wiki/sources/vitest-cli-guide.md — Bare `vitest` enters watch mode in a development environment and run mode in CI or a non-interactive terminal, `vitest watch` falls back to `vitest run` when stdin is not a TTY, and tools such as lint-staged should pass `--run` so the command exits.
Evidence: wiki/sources/jest-cli-options.md — Plain `jest` runs all tests by default; watch mode is opt-in with `--watch` or `--watchAll`.
Note: Verified against the current Vitest docs on 2026-10-11. The plan's correction ("can block", not "waits forever") holds. New: the agent-detection default means an agent's own bare `vitest` call may exit (how Vitest detects an agent is not documented), but a human terminal or an undetected agent harness with a TTY will still block, so the skill keeps recommending `vitest run`.

## Rule: Agent-written tests drift toward hollow and duplicated tests
Claim: Measured studies show coding agents add mocks to tests more often than other committers and that LLM-generated tests carry common smells such as Assertion Roulette and assertion-free tests, while agent tests add coverage on a par with human tests; no study yet measures snapshot-only, tautological or duplicated agent tests, so the audit looks for those test by test instead of presuming them.
Evidence: wiki/sources/coding-agents-over-mocked-tests.md — Across 2,168 TypeScript, JavaScript and Python repositories, 36% of coding-agent test commits add mocks against 26% for non-agents, and agents lean on the plain mock type (95% of their mocking commits) more than on fakes or spies; within the same repository the difference is small or negligible.
Evidence: wiki/sources/test-smells-in-llm-generated-unit-tests.md — Single-prompt LLM-generated Java test suites consistently show Assertion Roulette and Magic Number Test, and, at class level, up to 77% of suites with assertion-free tests, but human-written suites are dominated by the same smells and the smell detectors have high false-positive rates.
Evidence: wiki/sources/testing-with-ai-agents-empirical-study.md — Counter-evidence: in real TypeScript projects, agent-written tests were slightly longer with more assertions (median 2 against 1) and gave coverage gains comparable to or above human tests, on a small coverage sample.
Evidence: https://www.gitclear.com/ai_assistant_code_quality_2025_research — GitClear reports cloned lines rising and moved (reused) code falling in 2020 to 2024 as AI assistants spread; this is production code, correlational, and says nothing about tests specifically.
Opinion: "Hollow" (tests that cannot fail) and "duplicated" agent tests are this doctrine's expectation, not a measured result; a study that mutation-tests agent-written against human-written tests, or measures duplicate assertions across a suite by author, would confirm or overturn it.
Note: The seed claim ("agents tend to produce mock-only, snapshot-only, tautological and duplicated tests") was stronger than the evidence; only the mock part is measured, and the effect is modest.

## Rule: Risk tiers decide test depth
Claim: Risk-based testing selects, prioritizes and sizes test effort by risk level, the combination of how likely a failure is and how much harm it does; likelihood is better estimated from a component's history (age, change frequency, churn) and structural complexity than from the size of a change.
Evidence: wiki/sources/istqb-ctfl-syllabus-v4.md — ISTQB defines risk-based testing as selecting, prioritizing and managing test activities by risk analysis and control, with risk level set by likelihood and impact, and uses product risk analysis to set test scope, effort and priority.
Evidence: wiki/sources/what-makes-software-bugs-escape-testing.md — A 2026 study of over 14,000 defects found post-release defects concentrated in older, frequently modified, high-churn components.
Evidence: wiki/sources/deployment-risk-diff-aware-features-prime-video.md — Prime Video found lines added or deleted to be noisy predictors of deployment risk and structural code complexity a substantially stronger signal.
Note: James Bach's "Heuristic Risk-Based Software Testing" was sought but could not be captured (the satisfice.com download returned 404 to the clipper); it is queued in the vault's triage log and not cited here.

## Rule: Mutation testing measures whether a test can fail
Claim: Mutation testing seeds small faults into the code and checks whether the tests fail, so it measures a suite's ability to detect faults rather than the lines it executes; at scale it is practical only incrementally, on changed code.
Evidence: wiki/sources/practical-mutation-testing-at-scale.md — Petrović et al. describe mutation analysis as measuring a suite's ability to detect small seeded faults, "one of the strongest test-adequacy criteria", and make it practical at Google by mutating only changed code during code review.
Evidence: wiki/sources/stryker-what-is-mutation-testing.md — Stryker's docs explain that tests should fail against each mutant, that killed mutants measure test effectiveness, and that coverage misses assertion-free tests.
Evidence: wiki/sources/google-swe-book-testing-overview.md — Google warns that coverage only measures that a line was invoked, not what happened as a result.
Note: Only the abstract of Practical Mutation Testing at Scale is in the vault; the claim relies on nothing beyond it.
